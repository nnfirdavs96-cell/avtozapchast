# Глава 30. Индексы и почему всё тормозит

> **Часть VI. База данных** · Глава 30 из 60
> [← Глава 29](29-join.md) · [Глава 31 →](31-praktika-shema-bd.md)

## 🎯 Зачем эта глава

Пока в базе двенадцать товаров, любой запрос выполняется мгновенно. Кажется,
что о скорости думать рано.

Это самая распространённая ловушка. Сайт прекрасно работает у разработчика
на сотне тестовых записей — и ложится на боевом сервере, где записей сто тысяч.
Причём ложится не постепенно, а резко: вчера открывалось за полсекунды,
сегодня за двадцать.

В этой главе разберёмся, **почему** так происходит и как это лечится.
Тема простая, а эффект от неё больше, чем от всех остальных оптимизаций вместе.

## 📖 Индекс — это оглавление

Представьте телефонный справочник города на тысячу страниц, где фамилии записаны
**в случайном порядке**.

Найти Иванова — значит просмотреть все страницы подряд. В худшем случае —
всю книгу.

А теперь тот же справочник, но отсортированный по алфавиту. Иванова вы найдёте
за несколько секунд: открыли примерно на букве «И», уточнили, нашли.

**Индекс в базе — это отсортированная копия одного столбца** с указателями
на строки. База ищет по ней, а не перебирает таблицу.

### **Без индекса: полный перебор**

```sql
SELECT * FROM tovary WHERE artikul = 'W71280';
```

Без индекса база честно читает **каждую** строку и сравнивает артикул.
Сто тысяч строк — сто тысяч сравнений. Миллион строк — миллион.

Это называется **полное сканирование таблицы**, и оно линейно растёт вместе
с данными.

### **С индексом: поиск по отсортированному**

С индексом по `artikul` база идёт как по алфавиту: делит диапазон пополам,
отбрасывает половину, снова пополам. Чтобы найти одну строку среди миллиона,
хватает **двадцати шагов**.

## 📖 Замер на настоящих данных

Разговоры о скорости стоят мало, поэтому — измерим.

Я создал таблицу на **200 000 товаров** и выполнил один и тот же запрос
пять раз до создания индекса и пять раз после:

```sql
SELECT id, nazvanie, cena FROM tovary_mnogo WHERE artikul = 'ART00150000';
```

| | Время одного запроса |
|---|---|
| **Без индекса** | 18.4 мс |
| **С индексом** | 0.058 мс |
| **Разница** | **в 314 раз быстрее** |

Одна команда:

```sql
CREATE INDEX idx_artikul ON tovary_mnogo(artikul);
```

И запрос стал быстрее в сотни раз. Никаких изменений в коде, никакой
переделки логики.

**Вот почему индексы — первое, что проверяют, когда сайт тормозит.**

⚠️ Обратите внимание на порядок величин. 18.4 мс кажется терпимым.
Но страница каталога делает не один запрос, а десяток, и открывают её
одновременно сто человек. Умножьте — и получите лежащий сервер.

## 📖 Какие бывают индексы

```sql
-- Обычный: ускоряет поиск
CREATE INDEX idx_brend ON tovary(brend);

-- Уникальный: ускоряет И запрещает повторы
CREATE UNIQUE INDEX uniq_artikul ON tovary(artikul);

-- Составной: по нескольким столбцам сразу
CREATE INDEX idx_brend_cena ON tovary(brend, cena);

-- Полнотекстовый: для поиска по словам (только MySQL)
CREATE FULLTEXT INDEX ft_nazvanie ON tovary(nazvanie);
```

**Первичный ключ (`PRIMARY KEY`) — это тоже индекс**, создаётся автоматически.
Поэтому поиск по `id` всегда быстрый.

### **Составной индекс и правило левого края**

```sql
CREATE INDEX idx_brend_cena ON tovary(brend, cena);
```

Такой индекс работает для запросов:

```sql
WHERE brend = 'Bosch'                      -- ✅ работает
WHERE brend = 'Bosch' AND cena > 10000     -- ✅ работает
WHERE cena > 10000                         -- ❌ НЕ работает
```

Почему: индекс отсортирован **сначала по бренду, потом по цене внутри бренда**.
Как справочник, отсортированный по фамилии, а внутри одинаковых фамилий —
по имени. Найти всех Ивановых легко. Найти всех Сергеев — нет, придётся
перебирать всё.

**Правило левого края:** составной индекс работает, только если условие
включает **первый** столбец.

Отсюда практический вывод: порядок столбцов в составном индексе имеет значение.
Ставьте первым тот, по которому фильтруете чаще.

## 📖 Что индексировать

**Индексируйте:**

- поля, по которым **ищете**: `WHERE artikul = ...`;
- поля, по которым **соединяете**: `ON t.prodavec_id = p.id` — внешние ключи;
- поля, по которым **сортируете**: `ORDER BY cena`;
- поля, по которым **группируете**: `GROUP BY brend`.

**Не индексируйте:**

- всё подряд;
- поля, которые почти всегда одинаковые (`aktivnyi` со значением 1 у 99% строк);
- поля, которые не участвуют в запросах;
- очень длинные текстовые поля — для них есть `FULLTEXT`.

### **Почему нельзя индексировать всё**

У индексов есть цена, и её нужно понимать:

| Стоимость | Подробность |
|---|---|
| **Место на диске** | Индекс — отдельная структура. Пять индексов могут весить больше самой таблицы |
| **Замедление записи** | При каждом `INSERT` и `UPDATE` база обновляет **все** индексы таблицы |
| **Работа планировщика** | Чем больше индексов, тем дольше база выбирает, каким воспользоваться |

**Правило: индекс ускоряет чтение и замедляет запись.**

Для каталога товаров (читают тысячи раз, пишут раз в день) индексы — почти
всегда выигрыш. Для таблицы логов, куда пишут постоянно, а читают редко, —
наоборот.

## 📖 EXPLAIN — как узнать, что происходит

Гадать не нужно. База умеет рассказать, как она собирается выполнять запрос:

```sql
EXPLAIN SELECT * FROM tovary WHERE artikul = 'W71280';
```

В MySQL смотрите на три столбца:

| Столбец | На что смотреть |
|---|---|
| `type` | **`ALL` — плохо**: полный перебор. `ref`, `eq_ref`, `const` — хорошо |
| `rows` | Сколько строк база собирается просмотреть. Чем меньше, тем лучше |
| `key` | Какой индекс использовался. `NULL` — никакой |

**`type = ALL` на большой таблице — сигнал, что нужен индекс.**

В SQLite та же команда называется `EXPLAIN QUERY PLAN` и пишет по-человечески:
`SCAN tovary` (плохо) или `SEARCH tovary USING INDEX` (хорошо).

## 📖 Отчего ещё тормозит

Индексы — главная, но не единственная причина.

### **1. Проблема N+1 — самая частая**

```php
// ❌ Один запрос за списком...
$tovary = zapros('SELECT * FROM tovary LIMIT 20');

// ...и ещё двадцать за продавцами
foreach ($tovary as $t) {
    $prodavec = zapros('SELECT imya FROM prodavcy WHERE id = ?', [$t['prodavec_id']]);
}
```

Двадцать один запрос вместо одного. На странице с сотней товаров — сто один.

```php
// ✅ Один запрос с JOIN
$tovary = zapros('
    SELECT t.*, p.imya AS prodavec
    FROM tovary AS t
    LEFT JOIN prodavcy AS p ON p.id = t.prodavec_id
    LIMIT 20
');
```

**Это самая распространённая ошибка производительности в веб-разработке.**
Называется «проблема N+1»: один запрос за списком плюс N запросов за деталями.

Признак: страница открывается тем медленнее, чем больше на ней элементов.

### **2. `SELECT *` вместо нужных полей**

Тянете описание на две страницы для списка, где показываете только название.

### **3. `LIKE '%текст%'`**

Индекс не работает: искать «содержит» по отсортированному списку невозможно.
Решение — `FULLTEXT` или отдельный поисковый движок, глава 35.

### **4. Функция над индексированным полем**

```sql
WHERE YEAR(sozdan) = 2026            -- ❌ индекс не работает
WHERE sozdan >= '2026-01-01'
  AND sozdan <  '2027-01-01'         -- ✅ индекс работает
```

Как только вы оборачиваете столбец в функцию, база не может сопоставить его
с индексом. Переписывайте условие так, чтобы столбец остался «голым».

### **5. Огромный OFFSET**

```sql
SELECT * FROM tovary ORDER BY id LIMIT 20 OFFSET 100000;
```

База честно отсчитает сто тысяч строк и выбросит их. На последних страницах
каталога это заметно.

Решение — **пагинация по ключу**:

```sql
SELECT * FROM tovary WHERE id > 100000 ORDER BY id LIMIT 20;
```

Так делают ленту в соцсетях: вместо «страница 5000» — «показать ещё».

## 📖 Порядок действий, когда тормозит

Не гадайте — действуйте по списку:

1. **Найдите медленный запрос.** В MySQL включите журнал медленных запросов
   (`slow_query_log`). Он покажет, что именно тормозит.
2. **Прогоните через `EXPLAIN`.** Видите `type = ALL` — нужен индекс.
3. **Проверьте на N+1.** Посчитайте, сколько запросов делает страница.
   Больше десяти — почти всегда есть N+1.
4. **Создайте индекс и замерьте снова.** Обязательно замерьте: иногда
   помогает не то, что казалось.
5. **Только потом думайте о кэше.** Кэшировать медленный запрос — значит
   прятать проблему, а не решать её.

⚠️ **Порядок именно такой.** Новички начинают с пятого пункта — ставят кэш
поверх плохого запроса. Работает до первого случая, когда кэш протухнет
у всех разом.

## 💻 Индексы для нашего магазина

```sql
-- Артикул: ищем постоянно, повторов быть не должно
CREATE UNIQUE INDEX uniq_artikul ON tovary(artikul);

-- Фильтры каталога
CREATE INDEX idx_brend ON tovary(brend);
CREATE INDEX idx_kategoriya ON tovary(kategoriya);

-- Внешний ключ: соединяем при каждом показе каталога
CREATE INDEX idx_prodavec ON tovary(prodavec_id);

-- Составной под самый частый запрос каталога:
-- WHERE aktivnyi = 1 AND ostatok > 0 ORDER BY cena
CREATE INDEX idx_katalog ON tovary(aktivnyi, ostatok, cena);

-- Заказы
CREATE INDEX idx_zakaz_status ON zakazy(status);
CREATE INDEX idx_zakaz_sozdan ON zakazy(sozdan);
CREATE INDEX idx_zt_zakaz ON zakaz_tovary(zakaz_id);
CREATE INDEX idx_zt_tovar ON zakaz_tovary(tovar_id);

-- Поиск по названию
CREATE FULLTEXT INDEX ft_nazvanie ON tovary(nazvanie);
```

Обратите внимание на `idx_katalog`: столбцы идут в том порядке, в каком они
стоят в самом частом запросе каталога. Это не случайность — так составной
индекс покрывает и фильтр, и сортировку сразу.

## 🔤 Разбор по словам

| Запись | Что делает |
|---|---|
| `CREATE INDEX` | Создать индекс |
| `CREATE UNIQUE INDEX` | Индекс плюс запрет повторов |
| Составной индекс | По нескольким столбцам. **Работает от левого края** |
| `FULLTEXT` | Индекс для поиска по словам |
| `EXPLAIN` | Показать план выполнения |
| `type = ALL` | **Полный перебор.** Плохо |
| **N+1** | Один запрос за списком плюс N за деталями. Лечится `JOIN` |
| `slow_query_log` | Журнал медленных запросов |
| Пагинация по ключу | `WHERE id > N` вместо большого `OFFSET` |

## ⚠️ Грабли

**Тестировать на ста записях.** На боевых данных всё будет иначе.
Заливайте в тестовую базу хотя бы десятки тысяч строк.

**Индексировать всё подряд.** Запись замедлится, место кончится.

**Забыть индекс на внешнем ключе.** Каждый `JOIN` превращается в полный перебор.

**Функция над столбцом в `WHERE`.** Индекс перестаёт работать.

**Проблема N+1.** Считайте запросы на странице.

**Кэшировать вместо того, чтобы чинить.** Проблема остаётся и вернётся.

**Составной индекс не с того столбца.** Правило левого края: не тот порядок —
индекс бесполезен.

**Большой `OFFSET` на глубоких страницах.** Пагинация по ключу.

## 🔗 В бою

Откройте миграции в `sql/` этого репозитория и поищите `CREATE INDEX` или `KEY`.
Найдёте индексы на артикуле, бренде, идентификаторе продавца, статусе заказа —
ровно те, о которых шла речь.

Одна деталь из жизни проекта: в каталоге autodoc.tj поиск по названию идёт
**не по таблице товаров**, а по отдельному словарю `ae_part_dictionary`.
Причина как раз в этой главе: искать `LIKE '%фильтр%'` по большой таблице
с ценами и остатками недопустимо медленно. Словарь маленький, специально
проиндексирован и обновляется отдельно.

Такие решения не приходят сразу. Они появляются, когда база вырастает
и запрос, работавший за 50 мс, начинает занимать 5 секунд.

## 📌 Итог

- **Индекс — это оглавление.** Без него база перебирает все строки.
- Замер на 200 000 строк: **18.4 мс без индекса против 0.058 мс
  с индексом**. Разница в 314 раз.
- Индексируйте поля из `WHERE`, `JOIN`, `ORDER BY`, `GROUP BY`.
- **Индекс ускоряет чтение и замедляет запись.** Не индексируйте всё.
- Составной индекс работает **от левого края**.
- `EXPLAIN` показывает план. `type = ALL` — нужен индекс.
- **N+1** — главная ошибка производительности. Лечится `JOIN`.
- Функция над столбцом отключает индекс.
- Большой `OFFSET` медленный — пагинация по ключу.
- Порядок: найти → `EXPLAIN` → индекс → замерить. **Кэш последним.**
